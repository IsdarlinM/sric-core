# Sentinel Forge 0.5.0 Release Gate

Sentinel Forge 0.5.0 is releasable only when evidence proves every mandatory gate below for the exact commits being tagged.

## Repository gates

For each of the six repositories:

- `compileall` succeeds.
- Ruff succeeds.
- strict mypy succeeds.
- the complete pytest suite succeeds, including unit, integration, security, E2E CLI and property/fuzz tests.
- security scan and safety/AI eval hooks succeed when present.
- dependency audit succeeds.
- SBOM generation succeeds.
- wheel build succeeds.
- isolated wheel installation succeeds using the coordinated local 0.5 wheelhouse.
- every distributed CLI command supports both `--help` and `-h`; trailing `COMMAND help` remains supported by the entrypoint contract.
- `doctor` reports compatible SRIC/product versions and privacy-safe defaults.
- generated evidence records the exact commit SHA, tree SHA and dirty state.

## Ecosystem gates

`python sric-core/scripts/release-ecosystem.py --root .` must report `PASS` and prove:

- all six versions are compatible with the 0.5 release train;
- exact internal wheels can be built before publication;
- every individual repository gate passes;
- the cross-product contract smoke passes: Sentinel Case -> ReproSec context -> AuthTwin plan -> FossilScope plan -> TrustBoundary invariant -> Exposure DNA temporal view;
- no automated analysis promotes evidence to `VALIDATED` outside deterministic validation contracts.

## Platform/install/update gates

Evidence must cover:

- clean Windows installation through the `.cmd` installer and PATH availability;
- clean Linux installation through the idempotent `.sh` installer, PATH availability and uninstall;
- `tool update --check` and an actual 0.4/0.3-to-0.5 update path where applicable;
- preservation/backup of configuration and workspaces;
- migration rollback/failure behavior;
- no generated binaries or secrets committed to source control.

## Web UI gates

For each product Web UI:

- the application starts from the installed wheel;
- primary existing workflows and every newly exposed 0.5 analysis surface are reachable through real API-backed UI, or the release notes explicitly classify a surface as CLI/API-only with justification;
- desktop and mobile viewport browser E2E tests pass;
- no uncaught browser-console errors occur;
- evidence/provenance/confidence/limitations are visible for inferred outputs;
- controls never imply a validation or active action that the backend does not actually perform.

## Security regression gates

Mandatory regressions include, as applicable:

- SSRF and redirect target revalidation;
- path traversal, symlink and archive extraction safety;
- malicious/oversized import files and parser fuzzing;
- secret/token/cookie redaction;
- scope/policy/approval bypass attempts;
- prompt injection through untrusted external content;
- plugin permission bypass;
- migration tampering/failure;
- duplicated/upstream-dependent evidence and counter-evidence handling.

## Release decision

Do not merge/tag solely because code is versioned `0.5.0`. The release decision requires:

1. all individual `build/release-evidence/release-gate.json` documents to be `PASS`;
2. `sric-core/build/release-evidence/ecosystem-release-gate.json` to be `PASS`;
3. platform/install/update and browser-E2E evidence to be attached or referenced;
4. no unresolved P0/P1 security or correctness issue;
5. release artifacts, checksums, SBOM and signatures/attestations to correspond to the tested tree.

Until then, the six branches/PRs are **0.5.0 release candidates**, not validated releases.
