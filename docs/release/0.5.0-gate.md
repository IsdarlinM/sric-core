# Sentinel Forge 0.5.0 Release Gate

Sentinel Forge 0.5.0 is releasable only when evidence proves every mandatory gate below for the exact commits being tagged.

## Standalone Product Contract

Before integration testing, every repository must independently pass:

```bash
python -m sric.standalone_gate --root .
```

For each product this proves:

- the product depends directly on SRIC Core but not on sibling Sentinel Forge products;
- the installed console script exists;
- root `--help`, `-h` and `help` work;
- every registered command path is covered by recursive help/parser tests;
- unknown CLI options fail closed without tracebacks;
- `version`, `doctor` and `capabilities` execute successfully;
- the local Web root and capability API start without sibling products installed;
- standalone test evidence is tied to the source commit/tree when Git metadata is available.

Across all six repositories:

```bash
python sric-core/scripts/release-standalone-ecosystem.py --root .
```

must produce `sric-core/build/release-evidence/ecosystem-standalone-gate.json` with `PASS` before the integrated ecosystem gate is considered.

## Repository gates

For each of the six repositories:

- `compileall` succeeds.
- Ruff succeeds.
- strict mypy succeeds.
- the complete pytest suite succeeds, including unit, integration, security, E2E CLI, standalone and property/fuzz tests.
- security scan and safety/AI eval hooks succeed when present.
- dependency audit succeeds.
- SBOM generation succeeds.
- wheel build succeeds.
- isolated wheel installation succeeds using the coordinated local 0.5 wheelhouse.
- every distributed CLI command supports `--help`, `-h` and trailing `COMMAND help`.
- `doctor` reports compatible SRIC/product versions and privacy-safe defaults.
- `capabilities` reports absent sibling products as optional rather than errors and suppresses capabilities from incompatible release trains.
- generated evidence records the exact commit SHA, tree SHA and dirty state.

## Ecosystem gates

`python sric-core/scripts/release-ecosystem.py --root .` must report `PASS` and prove:

- all six versions are compatible with the 0.5 release train;
- exact internal wheels can be built before publication;
- every individual repository gate passes;
- the cross-product contract smoke passes: Sentinel Case -> ReproSec context -> AuthTwin plan -> FossilScope plan -> TrustBoundary invariant -> Exposure DNA temporal view;
- no automated analysis promotes evidence to `VALIDATED` outside deterministic validation contracts.

## Platform/install/update gates

Evidence must cover:

- clean Windows installation through each `.cmd` installer in a fresh temporary profile;
- clean Linux installation through each idempotent `.sh` installer in a fresh temporary HOME;
- installers resolve SRIC 0.5 as a normal package dependency and never silently consume adjacent sibling repositories;
- installed `doctor` and `capabilities` checks pass before an installer declares success;
- Linux uninstall removes runtime files while preserving workspaces, capsules, configuration and evidence;
- `tool update --check` and an actual prior-version-to-0.5 update path where applicable;
- migration backup/rollback/failure behavior;
- no generated binaries or secrets committed to source control.

## Web UI gates

For each product Web UI:

- the application starts from the installed wheel with no sibling product installed;
- the capability endpoint accurately reflects optional integrations;
- primary workflows and every newly exposed 0.5 analysis surface are reachable through real API-backed UI, or release notes explicitly classify a surface as CLI/API-only with justification;
- desktop and mobile viewport browser E2E tests pass;
- no uncaught browser-console errors occur;
- evidence/provenance/confidence/limitations are visible for inferred outputs;
- controls never imply validation or active execution that the backend does not perform;
- no product exposes an arbitrary operating-system web shell.

## Security regression gates

Mandatory regressions include, as applicable:

- SSRF and redirect target revalidation;
- path traversal, symlink and archive extraction safety;
- malicious/oversized import files and parser fuzzing;
- secret/token/cookie redaction;
- scope/policy/approval bypass attempts;
- prompt injection through untrusted external content;
- plugin permission bypass;
- migration tampering/failure;
- duplicated/upstream-dependent evidence and counter-evidence handling.

## Release decision

Do not merge/tag solely because code is versioned `0.5.0`. The release decision requires:

1. all individual `build/release-evidence/standalone-gate.json` documents to be `PASS`;
2. `sric-core/build/release-evidence/ecosystem-standalone-gate.json` to be `PASS`;
3. all individual `build/release-evidence/release-gate.json` documents to be `PASS`;
4. `sric-core/build/release-evidence/ecosystem-release-gate.json` to be `PASS`;
5. platform/install/update and browser-E2E evidence to be attached or referenced;
6. no unresolved P0/P1 security or correctness issue;
7. release artifacts, checksums, SBOM and signatures/attestations to correspond to the tested tree.

Until then, the six branches/PRs are **0.5.0 release candidates**, not validated releases.
